# Orders

TypeScript, Fastify и PostgreSQL. Сервис выполняет оба задания.

`POST /orders` сохраняет заказ и отвечает `201 pending`. Обработка идёт в фоне:
резерв товара, оплата, затем `paid` или снятие резерва и `rejected`, если банк
ответил `402`. Состояние обработки хранится в таблице `orders`, поэтому после
перезапуска сервис продолжает незавершённые заказы.

## Повторные запросы и отказы

- Ключ оплаты равен номеру заказа и не меняется при повторе. Тело платежа берётся
  из сохранённого заказа. Потерянный ответ проверяется через `GET /payments`.
- После трёх ошибок обращения к Payment приостанавливаются на пять секунд.
  Затем допускается один пробный запрос. Одновременно обрабатываются до четырёх
  заказов; HTTP-ответ покупателю не ждёт банка.
- Резервирование и снятие резерва можно повторить по тому же `order_id`.
  Отказ банка сохраняется до снятия резерва, чтобы после сбоя не резервировать
  товар заново.
- Статус `paid` и запись в `outbox` фиксируются одной транзакцией. События
  отправляются отдельным обработчиком. Если ответ шины потерялся, отправка
  повторяется с прежним `id`.
- Входящее событие записывается в `inbox` по уникальному `id`. Запись события и
  увеличение баланса выполняются одной транзакцией. Дубликат получает `204`,
  но не увеличивает баланс.

Сетевой запрос ограничен четырьмя секундами. Повторы используют задержку от
0,5 до 5 секунд. Заказ с нулевой суммой резервируется и завершается без обращения
к банку. Числа в HTTP API ограничены точным диапазоном целых чисел JavaScript.

## Проверка

Из `orders`:

```sh
npm ci
npm test
npm run format:check
```

Интеграционные тесты требуют отдельной PostgreSQL с базой `orders_test`:

```sh
TEST_DATABASE_URL=postgres://orders:orders@localhost:54329/orders_test npm run test:integration
```

Тесты очищают только эту тестовую базу. Они проверяют параллельные дубликаты,
откат транзакций, валидацию и потерю ответа при оплате.

Из корня стенда:

```sh
make scenarios TASK=1
make scenarios TASK=2
```

## Ограничения

Расчёт на один экземпляр Orders, как в условии. Для нескольких экземпляров
понадобится координация фоновых обработчиков. При недоступности Postgres сервис
не может подтвердить сохранение заказа. Таблицы заказов, отправленных событий и
обработанных доставок растут; очистка потребовала бы отдельного правила хранения
и согласованного срока возможного повтора событий.
