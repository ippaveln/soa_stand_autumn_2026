# Решение заданий 1 и 2

`main.go` принимает HTTP-запросы и создаёт схему Postgres, `workflow.go`
завершает заказы в фоне, `events.go` публикует события и начисляет бонусы.
Дополнительных зависимостей относительно исходного Go-примера нет.

## Оформление заказа

`POST /orders` проверяет тело и сумму, сохраняет заказ со статусом `pending`
и сразу возвращает `201`. Покупатель ждёт только запись в Postgres;
доступность Payment, Inventory и шины на длительность запроса не влияет.

Фоновый обработчик читает незавершённые заказы из базы:

1. `reserve`: резервирует товар по ID заказа и сохраняет этап `pay`.
2. `pay`: отправляет оплату с `Idempotency-Key`, равным ID заказа.
   Подтверждённая оплата переводит заказ в `paid`, отказ банка `402` — на
   этап `release`.
3. `release`: снимает резерв и только после подтверждения ставит `rejected`.

Повторные резервирование и снятие резерва безопасны по контракту Inventory.
Платёж всегда повторяется с прежними ключом, суммой и валютой. Тайм-аут,
обрыв соединения и `500` не означают отказ банка: заказ остаётся `pending`.
После неопределённого результата обработчик проверяет списания через GET.
Если списания ещё не видно, он повторяет оплату с прежним ключом.
Для медленного ответа без списания время ожидания фонового повтора растёт.

Общий circuit breaker при недоступности Payment делает паузу между пробами.
Он принадлежит одному обработчику заказов, поэтому отдельные заказы не
создают собственный поток запросов к недоступному банку.

## События и бонусы

У каждой строки заказа есть `event_sent`. Строки `paid` с `event_sent=false`
составляют outbox: перевод в `paid` одновременно сохраняет обязанность
отправить событие. После ответа шины `202` обработчик отмечает отправку.
ID события получается из типа `order.paid` и ID заказа.

Если процесс упал после публикации, но до отметки в базе, он опубликует копию
с тем же ID. Если упал после оплаты, но до записи `paid`, повтор с прежним
ключом получит результат прежнего платежа. Незавершённые этапы и outbox
восстанавливаются из базы при запуске.

Входящая доставка записывается в `delivery_events` с уникальным ID события
через `INSERT ... ON CONFLICT DO NOTHING`. Сама запись является начислением;
баланс — сумма записей покупателя. Поэтому нет промежутка между отметкой
«обработано» и изменением баланса, а параллельные копии не удваивают бонусы.
Ответ `204` отправляется после завершения INSERT.

## Проверка

```sh
make scenarios TASK=1
make scenarios TASK=2
cd orders
go test -mod=readonly -race ./...
go vet -mod=readonly ./...
```

При занятом порте `8080` можно добавить `ORDERS_PORT=18080` к `make`.
Интеграционные тесты требуют `TEST_DATABASE_URL`: они создают отдельную
схему на тест и удаляют только её. Без переменной эти тесты пропускаются.
Проверяются потеря ответа, медленная оплата и отказ банка, общий breaker,
восстановление этапов, повтор исходящего события и параллельные доставки.

Локальная проверка 26.10.2026:

- Задание 1: S1–S5, **5/5 PASS**, уровень «полностью».
- Задание 2: S1 и S6–S8, **4/4 PASS**, уровень «полностью».
- Оба прогона — с обычной паузой 30 секунд. Отчёты — в `results/task_1.html`
  и `results/task_2.html` относительно корня репозитория.
- Все Go-тесты с настоящим Postgres, модульные тесты с `-race` и `go vet`
  прошли. В S4 за минуту отказа было 22 обращения к Payment при лимите 30.

## Границы решения

Стенд запускает один экземпляр Orders; обработчики не координируются между
несколькими экземплярами. Заказы и журнал начислений сохраняются в базе:
с ростом данных нужны правила хранения. Журнал доставок нельзя просто
очистить, пока шина может прислать старое событие повторно. Отказ самого
Postgres не маскируется успешным приёмом: без записи заказ не принимается,
а доставка получает ошибку, чтобы шина повторила её.
